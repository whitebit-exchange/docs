## Cancel order

### Request parameters

<WsSchemaTable fields={orderCancelParams} />

The `market` parameter routes the call, so it stays required even when the order id alone would identify the order. When both identifiers are supplied, `client_order_id` takes precedence — the response still reports the engine id, which confirms which order was hit.

<WsMessageExample data={exOrderCancelRequest} />

Canceling by client order id follows the same shape:

```json
{
  "market": "ETH_USDT",
  "client_order_id": "pws_cancel_1786452693420"
}
```

### Response

<WsMessageExample data={exOrderCancelResponse} />

The `result` object is the standard order object with `status` `CANCELED` — see the [order object reference](/websocket/order-management/overview#order-object). The `mtime` field advances to the cancellation time while `ctime` stays at placement, so the pair tells how long the order lived.

<Warning>Verify the outcome by status, not by the absence of an error. A successful call returns `CANCELED`; an unknown or already-finished order returns error `6`. A partially filled order reports its matched quantity in `deal_stock` — cancellation withdraws only the remainder in `left`.</Warning>

<Note>Groups need a different call. Use [`order_cancel_conditional`](/websocket/order-management/order-cancel-conditional) for OCO and OTO groups — passing a group id here returns error `6`. Plain stop orders and TPSL legs, on the other hand, belong to this method.</Note>

## Update frequency

This method is client-initiated: the server answers each `order_cancel` request with a single response frame carrying the same `id`. Subscribe to [Orders Pending](/websocket/account-streams/orders-pending) to observe the cancellation event.
