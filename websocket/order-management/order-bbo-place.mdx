## Place BBO order

### Request parameters

<WsSchemaTable fields={orderBboPlaceParams} />

The `bbo_role` parameter decides which side of the spread supplies the price.

| Role | Price source | Effect |
|------|-------------|--------|
| `1` maker | Own-side best — the best bid for a buy | Adds liquidity; `post_only` is set implicitly |
| `2` taker | Opposite-side best — the best ask for a buy | Crosses the spread and matches immediately |

Sending `post_only` together with `bbo_role: 2` is rejected as a wrong flag combination, because a taker order cannot be post-only. With `bbo_role: 1` the flag is redundant but accepted.

### Response

<WsMessageExample data={exOrderBboPlaceResponse} />

The response is an ordinary limit order reporting `type` `1` — no BBO marker survives placement. The `price` field records where the order landed. See the [order object reference](/websocket/order-management/overview#order-object).

<Warning>No re-pegging happens. The price is resolved once, at placement, and the order then behaves like any other resting limit order as the order book moves away from it. Re-quoting requires canceling and placing again, or [`order_modify`](/websocket/order-management/order-modify).</Warning>

## Update frequency

This method is client-initiated: the server answers each `order_bbo_place` request with a single response frame carrying the same `id`.
