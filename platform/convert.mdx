Convert provides instant currency conversion at a quoted rate. Unlike [spot trading](/products/spot/overview), Convert requires no orderbook interaction — request a quote and confirm it before it expires, or do both in a single call, and the conversion executes immediately.

## When to use Convert

| Feature | Convert | Spot Trading |
|---------|---------|-------------|
| Execution | Instant at quoted rate | Depends on orderbook liquidity |
| Orderbook | No orderbook interaction | Orders placed on the orderbook |
| Order types | Single quote-and-confirm flow | 6 order types (limit, market, stop-limit, stop-market, OCO, bulk) |
| Best for | Quick conversions, price estimation | Advanced trading strategies, precise price control |

<Note>
  Convert also serves as a price estimation tool. Call the estimate endpoint before placing a market order to preview the approximate execution price. The estimate checks the Trade balance first, so the amount must be available on the Trade balance.
</Note>

## Balances

Convert through the API uses the Trade balance for both legs: the conversion takes the source currency from the [Trade balance](/api-reference/trading/trading-balance) and puts the converted amount on the Trade balance. When the source currency is not on the Trade balance, the request fails with the insufficient-balance error and no funds move. Transfer the source currency from Main to Trade with [Transfer between balances](/api-reference/account-wallet/transfer-between-balances) before converting (in the transfer request, the Trade balance is `spot` in the `from` and `to` fields), and request the estimate after the transferred amount shows on the Trade balance. The withdrawal endpoints debit the Main balance, so transfer the converted amount back to Main and withdraw after the amount shows on the [Main balance](/api-reference/account-wallet/main-balance) (`POST /api/v4/main-account/balance`).

A transfer returns `201` with an empty array (`[]`). The `201` means the platform accepted the transfer, not that the funds moved, so read the Trade balance (`POST /api/v4/trade-account/balance`) until the amount shows.

The transfer request takes no idempotency key, and a transfer can still complete after a timeout or a `5xx`. A matching record in [Get transfer history](/api-reference/account-wallet/get-transfer-history) means the transfer completed. No record can also mean the transfer is still queued, so repeat the check and do not resend automatically. A transfer that never shows is a manual check, as the between-balances row in [Retry strategy by error type](/api-reference/rate-limits#retry-strategy-by-error-type) describes.

## Conversion flow

The quoted-rate flow has two steps: estimate and confirm.

<Steps>
  <Step title="Request a quote">
    Send a `POST` request to [`/api/v4/convert/estimate`](/api-reference/convert/convert-estimate) with the following parameters: `from` (source ticker), `to` (destination ticker), `direction` (`"from"` or `"to"`), and `amount`. The response includes `id` (quote identifier), `give`, `receive`, `rate`, and `expireAt`.
  </Step>
  <Step title="Confirm the quote">
    Send a `POST` request to [`/api/v4/convert/confirm`](/api-reference/convert/convert-confirm) with `quoteId` set to the `id` returned by the estimate. The response returns `finalGive` and `finalReceive`.
  </Step>
</Steps>

<Note>
  Each estimate response includes an `expireAt` timestamp in Unix seconds — confirm before that moment. Honor the value returned per quote rather than hard-coding a fixed window. If the quote expires before confirmation, request a new estimate.
</Note>

[Convert Auto Confirm](/api-reference/convert/convert-auto-confirm) collapses both steps into one request: the quote is requested and accepted in one call, so no expiry window applies and no `quoteId` round-trip is needed. The endpoint accepts an optional idempotency key that makes a retry safe within the limits in [Convert Auto Confirm](/api-reference/convert/convert-auto-confirm); see also [Results and retries](#results-and-retries).

## Results and retries

A `200` response means the conversion executed, and a request that fails never returns `200`. When two conversions compete for the same funds, only one executes; the other returns the insufficient-balance error. Two `200` responses with the same `id` come only from two auto-confirm requests with the same idempotency key, and describe one conversion. Key the partner's ledger on the quote ID: the `id` from Auto Confirm, or the `quoteId` sent to Confirm.

A quote executes in full at the quoted amounts or not at all. With `direction: "to"`, the amount received equals the requested amount exactly, because the platform builds the fee into the amount given. Rarely, the platform refuses a confirm when the price moves after the estimate. The platform then converts nothing; request a new estimate.

The following responses leave the outcome open, and the conversion may have executed:

| Response | Find the outcome |
|----------|------------------|
| Confirm: `400` with code `0`, or any `5xx` | Look up the `quoteId` in [Convert History](/api-reference/convert/convert-history). |
| Auto Confirm: `500` (the API timed out before the conversion service returned an outcome; the conversion can still complete) | With an idempotency key, resend the identical request with the same key, as the rules below the table describe. Without a key, search Convert History by time window, pair, and amounts. |
| Auto Confirm: `502` (the conversion service returned no outcome) | Search Convert History by time window, pair, and amounts. A retry with the same key returns the same `502`. |

A resend with an idempotency key follows these rules:

- Within 24 hours, the endpoint returns the original response, or `409` while the conversion is still running; retry later with the same key.
- If processing stops without recording an outcome, the claim on the key lapses after 60 seconds, and a retry with the same key can then convert a second time.
- A resend that comes more than 60 seconds after the first request needs a Convert History check by time window, pair, and amounts first.
- After 24 hours, a resend with the same key can convert a second time.

A record in Convert History means the conversion executed and the converted amount is on the Trade balance. The platform writes the record when the conversion executes, so a conversion that executed appears in the history at once. After a confirm that executed, a retry of the same quote returns code `24`, so look up the `quoteId` before requesting a new estimate.

<Warning>
  A confirm of a new quote, or an auto-confirm with a new idempotency key, can convert the same funds a second time. Check Convert History before converting the same funds again.
</Warning>

[Convert Auto Confirm](/api-reference/convert/convert-auto-confirm) describes how long the platform holds a key.

## API endpoints

Convert uses 4 authenticated endpoints. All require HMAC-SHA512 signing. Before the first conversion, the account owner accepts the Convert terms once on whitebit.com; sub-accounts do not accept the terms separately. Until then, the estimate and auto-confirm endpoints return `Terms of exchange are not accepted`.

| Endpoint | Purpose | Rate limit |
|----------|---------|------------|
| [`POST /api/v4/convert/estimate`](/api-reference/convert/convert-estimate) | Request a conversion quote | 10,000 req / 10 sec |
| [`POST /api/v4/convert/confirm`](/api-reference/convert/convert-confirm) | Confirm and execute a quote | 10,000 req / 10 sec |
| [`POST /api/v4/convert/auto-confirm`](/api-reference/convert/convert-auto-confirm) | Request and accept a quote in a single call | 10,000 req / 10 sec |
| [`POST /api/v4/convert/history`](/api-reference/convert/convert-history) | Retrieve conversion history (up to 180 days back, 30 days per request) | 10,000 req / 10 sec |

## Estimate parameters

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `from` | string | Yes | Source currency ticker (e.g., `BTC`) |
| `to` | string | Yes | Destination currency ticker (e.g., `USDT`) |
| `direction` | string | Yes | `"from"` = amount is in source currency; `"to"` = amount is in destination currency |
| `amount` | string | Yes | Amount to convert or receive |

## Code example

Estimate a BTC-to-USDT conversion and confirm the quote.

    ```bash
      -H "X-TXC-PAYLOAD: YOUR_PAYLOAD" \
      -H "X-TXC-SIGNATURE: YOUR_SIGNATURE" \

      -d '{
        "from": "BTC",
        "to": "USDT",
        "direction": "from",
        "amount": "1",
        "request": "/api/v4/convert/estimate",
        "nonce": 1
      }'
    ```

    ```json
      "to": "USDT",

      "expireAt": 1699016476
    }
    ```


## History filters

The [history endpoint](/api-reference/convert/convert-history) supports filtering by `fromTicker`, `toTicker`, `quoteId`, and time range (`from`/`to` timestamps). The default limit is 100 records. The maximum history depth is 180 days, counted back from the time of the request. Each request covers at most 30 days between `from` and `to`, and `from` defaults to 30 days before the request. The endpoint rejects a wider range with `422`. Reading the full 180 days takes consecutive requests of up to 30 days each.

## Convert in payment flows

Withdrawal flows commonly use Convert when the currency held in Main balance differs from the currency an end user needs to withdraw. The pattern has five steps:

1. Transfer the source currency from Main to Trade, and wait until the amount shows on the Trade balance.
2. Request an estimate.
3. Confirm the quote.
4. Transfer the converted amount from Trade to Main, and wait until the amount shows on the Main balance.
5. Submit the withdrawal in the destination currency.

No field ties a conversion to the withdrawal that spends it. Store the quote ID of each conversion in the partner's ledger. Put a reference unique to the withdrawal in its `uniqueId` (up to 255 characters), and map that reference to the quote IDs of the conversions the withdrawal spends.

For the full step-by-step withdrawal-with-conversion flow including code examples, see [Payment Integration](/guides/payment-integration).
