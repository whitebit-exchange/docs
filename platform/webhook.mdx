## Why Webhooks?

Webhooks deliver real-time HTTP notifications when events occur on a WhiteBIT account — deposits arriving, withdrawals completing, codes being applied, and refunds processing. Without webhooks, the only alternative is polling the deposit/withdrawal history endpoints repeatedly.

**Webhooks vs polling:**

| | Webhooks | Polling |
|---|---|---|
| Latency | Real-time (seconds) | Depends on polling interval |
| Server load | Event-driven — no wasted requests | Constant requests, mostly empty |
| Reliability | ~3 delivery attempts spaced roughly hourly over a ~1-day window | As reliable as the polling loop |
| Recommended for | Production payment flows | Fallback for outages exceeding the delivery window |

<Note>
  There is no webhook replay mechanism. If every delivery attempt fails, the event is dropped. Implement polling of the [deposit / withdrawal history](/api-reference/account-wallet/get-deposit-withdraw-history) endpoint as a fallback so events can be reconciled after extended consumer downtime.
</Note>

**Common use cases:**
- **Payment processing** — Detect incoming deposits and credit end users automatically
- **Withdrawal monitoring** — Track withdrawal lifecycle from creation to completion or cancellation
- **Code redemption** — Receive notification when a WhiteBIT Code is applied
- **Refund handling** — Detect successful or failed refunds for reconciliation
- **Virtual account monitoring** — Receive bank details when a virtual account becomes active, without polling the status endpoint

## How to use

A webhook is a separate entity with its own generated key and secret. It is not a property of a trading API key, and a trading API key never carries a webhook URL.

An account has at most one webhook. The platform enforces this limit, so a second webhook cannot be created on the same account. A sub-account counts as a separate account, so the main account and each sub-account can have one webhook.

Event types are selected on the webhook itself, so a single URL receives every event type subscribed on it.

1. Log in to whitebit.com.
2. Open the API keys tab.
3. Select the web-hook configuration tab.
4. Paste the correct URI for the web server to process web-hook calls.
5. Press Generate a new key button and toggle the activation switcher to "Activated".

<Warning>
The secret key is shown only once. Save it in a secure key store.
</Warning>

## Requirements

### For web hook keys generation

Before using webhooks, verify ownership of the domain set as the webhook destination. Use one of three methods:

1. Add a TXT DNS record to the domain with the webhook public key.
2. Add the plain text file `whiteBIT-verification.txt` to the root domain folder and provide public web access. Place the public webhook key in the file.
3. Implement the `/whiteBIT-verification` endpoint to respond with 200 OK and return a JSON array containing the public webhook key. Example: `["<public-webhook-key>"]`

Passing one of these checks enables the webhook.

### For processing web-hook requests

All web hook requests are performing using POST method and with application/json content type. Consumer server should respond with 200 HTTP status code. If the consumer cannot handle the webhook, the platform retries delivery a small number of times spaced roughly an hour apart, over a window of about one day. Treat the exact cadence as best-effort, not a contract, and pair webhook consumption with periodic history polling for reconciliation.

#### Body data

All web-hook requests are performing with

```json
{
  "method": "string",
  "params": {
    "nonce": 0
  },
  "id": "uniqueID"
}
```

**method** - string. The name of method which was evaluated. Web hooks API supports such web-hook methods:

- **code.apply**. Performs when code owned by a customer was applied.

**id** - string. Uuid to identify every request.

**params** - the request payload. Contains data about the actions triggering the webhook call. The field also contains a [nonce](/glossary#nonce). **'nonce'** - a number always **greater** than the previous request’s nonce number

#### Request headers

Also, all request contains additional data in headers:

1. `'Content-type': 'application/json'`
2. `'X-TXC-APIKEY': api_key` - the WhiteBIT webhook API key
3. `'X-TXC-PAYLOAD': payload'` - where payload is base64-encoded body data
4. `'X-TXC-SIGNATURE': signature` - where signature is `hex(HMAC_SHA512(payload), key=api_secret))`. `api_secret` is the secret of the generated webhook key.

On the consumer side, process the security headers to verify the request originated from WhiteBIT.

Performed when [code](/glossary#whitebit-codes) was applied. Request example:

```json
{
  "method": "code.apply",

    "nonce": 1
  },
  "id": "45a1d85d-2fdf-483e-8dfa-6d253148c730"

```

#### Travel Rule deposit statuses (EEA)

For EEA users, an inbound deposit may be frozen pending Travel Rule verification, and the deposit carries a Travel Rule status code (see the table below). There is currently no webhook for these transitions, so track status changes via the [deposit/withdraw history](/api-reference/account-wallet/get-deposit-withdraw-history). When the Travel Rule API is enabled for the account, submit the deposit originator data via [Submit deposit originator data](/api-reference/travel-rule/submit-deposit-verification) (`POST /api/v4/travel-rule/deposit/verification`); otherwise the deposit is verified manually at whitebit.com. Funds are credited only after successful verification.

For details on Travel Rule requirements and the travelRule object for withdrawals, see [Regulatory Compliance](/institutional/compliance).

Deposit status codes:

| Code | Status | Description |
|---|---|---|
| 15 | Pending | Deposit detected, awaiting confirmations |
| 27 | Travel Rule Frozen | Deposit frozen; the user must complete Travel Rule verification (EEA) |
| 28 | Travel Rule Frozen Processing | Travel Rule data submitted, verification in progress (EEA) |

### WhiteBIT virtual account status

Performed when the status of a [virtual account](/glossary#virtual-account) changes. The `deposit.virtual_account_status` event removes the need to poll [Get virtual account status](/api-reference/account-wallet/get-virtual-account-status) for status changes; polling remains available. The event covers virtual accounts of every provider, including accounts registered through the WhiteBIT interface.

To receive the event, enable the virtual account status event in the deposit group of the webhook configuration. On a webhook created before the event was introduced, the event is disabled by default and existing event subscriptions do not change. A webhook activated for the first time subscribes to every event, including `deposit.virtual_account_status`.

The platform sends the event on every status change of the virtual account:

- **Activation** — the provider allocates the account, and `status` becomes `active`.
- **Rejection** — the provider refuses to open the account, and `status` becomes `rejected`.
- **Closure** — the provider closes the account, and `status` becomes `closed`. A closure attempt that leaves the account open does not trigger the event.

Registration does not trigger the event: the initial `pending` status that [Create virtual account](/api-reference/account-wallet/create-virtual-account) returns is not a status change. Deposits to the virtual account do not trigger the event either; deposit status changes arrive as the `deposit.*` events above. The platform sends the event only after Get virtual account status returns the new status, so both sources report the same status for the same account. Request example:

```json
{
  "method": "deposit.virtual_account_status",
  "params": {
    "provider": "SEPA_BCB_GROUP",
    "status": "active",
    "paymentDetails": {
      "beneficiary": "Acme Trading Ltd",
      "iban": "DE89370400440532013000",
      "bic": "COBADEFFXXX"
    },
    "timestamp": 1761566400,
    "nonce": 1
  },
  "id": "uuid"
}
```

| Field | Type | Description |
|---|---|---|
| `provider` | String | [Fiat](/glossary#fiat) [provider](/glossary#provider) of the virtual account, for example `SEPA_BCB_GROUP`. |
| `status` | String | New status of the virtual account. Uses the same values as `status` in Get virtual account status. |
| `paymentDetails` | Object | Bank details for incoming bank transfers, with the same fields as `paymentDetails` in Get virtual account status. Contains data only when `status` is `active`. For other statuses, the field is an empty object `{}`. |
| `timestamp` | Integer | Time the platform registered the status change, as a Unix timestamp in seconds. Retries carry the original value. Compare `timestamp` with the last processed value to discard a notification that arrives out of order. |
| `nonce` | Integer | Request [nonce](/glossary#nonce), common to every webhook request. |

<Warning>
The event carries the bank details that end users send deposits to. Verify the `X-TXC-SIGNATURE` header as described in [Request headers](#request-headers) before using `paymentDetails`.
</Warning>

Delivery follows the retry policy in [Processing webhook requests](#for-processing-web-hook-requests). A failed delivery does not change the virtual account status. After the last retry fails, the platform drops the notification; use Get virtual account status to read the current status and bank details.

### WhiteBIT refund successful

Triggered after the system successfully completes a refund. `memo` is the destination memo sent in the [refund request](/api-reference/account-wallet/refund-deposit). Unlike deposit and withdraw webhooks, which send `""`, refund webhooks send `null` when no memo was provided. Request example:

```json
{
  "method": "refund.successful",
  "params": {
    "transactionId": "5e112b38-...",
    "status": "completed",
    "refundAddress": "GDTSOI56...",
    "depositAmount": "100",
    "currency": "Tether USDT",
    "ticker": "USDT",
    "network": "ERC-20",
    "createdAt": 1733924412,
    "processedAt": 1733925012,
    "refundNetworkFee": "1",
    "refundAmount": "99",
    "refundHash": "0x767ebd2...",
    "memo": null, // refund destination memo, null if not provided
    "nonce": 0
  },
  "id": "uuid"
}
```

### WhiteBIT refund failed

Triggered after the system fails to complete a refund. The system rejects the refund if the destination address does not support the required network or asset, or if validation fails. Use a different address or contact support. Request example:

```json
{
  "method": "refund.failed",
  "params": {
    "transactionId": "5e112b38-...",
    "status": "failed",
    "refundAddress": "GDTSOI56...",
    "depositAmount": "100",
    "currency": "Tether USDT",
    "ticker": "USDT",
    "network": "ERC-20",
    "createdAt": 1733924412,
    "processedAt": 1733925012,
    "memo": null, // refund destination memo, null if not provided
    "nonce": 0
  },
  "id": "uuid"
}
```

<Note>
`refund.failed` is also sent when a refund attempt fails for an internal reason. In that case, [Get refund history](/api-reference/account-wallet/get-refund-history) still shows the refund as `in_process` and the refund is not final. A refund with status `canceled` in the refund history is final.
</Note>
