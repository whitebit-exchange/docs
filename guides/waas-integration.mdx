<Note>
**For developers.** This page covers the technical integration. For what WaaS is, the verification variants at a
business level, and how to apply, see the [WaaS overview](/guides/waas-overview).
</Note>

WaaS runs on Model A, a partner-operated sub-account per end user (see
[Integration models](/concepts/integration-models)). Account creation, per-sub-account API keys, and KYC
URLs are documented in [Account architecture](/guides/sub-account-integration#account-architecture) and
[Customer onboarding flow](/guides/sub-account-integration#customer-onboarding-flow); this guide covers
the wallet flows on top.

## Prerequisites

- **Approved WaaS partner enrollment** — see the [WaaS overview](/guides/waas-overview) for what WaaS provides and how to apply.
- **A chosen verification variant** — managed sub-accounts, KYC reliance, or shared-KYC sub-accounts; see [Build path per variant](#build-path-per-variant).
- **API access** — [HMAC-signed requests](/api-reference/authentication); a `type: 2` API key (deposits and withdrawals) on each sub-account, with the URLs the integration calls enabled (every URL group starts switched off on a new key); crypto deposits to sub-accounts and the sub-account withdrawal endpoints enabled for the account by the account manager.
- **Sub-account limit** — a main account holds up to 50 sub-accounts by default; the assigned account manager raises the limit on request.

## Build path per variant

- **Managed sub-accounts.** The partner creates a sub-account per end user under the main account (`POST /api/v4/sub-account/create` with `shareKyc: false` and the end user's `email`). WhiteBIT emails the end user an invitation, and the sub-account is activated once the end user opens the link and sets a password. WhiteBIT then verifies each end user through a KYC URL; transfers from the main account to the sub-account are refused until the KYC is approved. Build with [Sub-Accounts](/products/sub-accounts/overview) for account creation and management, and the [customer onboarding flow](/guides/sub-account-integration#customer-onboarding-flow) for the KYC URL and per-customer API keys.
- **Sub-accounts with KYC reliance.** The same sub-account architecture as the managed variant, but the partner performs end-user KYC instead of WhiteBIT, under a Compliance-approved agreement. The partner creates each sub-account with `shareKyc: true` and no `email`, so the sub-account is active at creation with no invitation step; a request with `email` starts the invitation flow instead. Build with the same [Embedded Trading integration guide](/guides/sub-account-integration); complete [Institutional Onboarding](/institutional/onboarding) first to establish the reliance agreement. See [KYC reliance eligibility](#kyc-reliance-eligibility) below for the conditions.
- **Shared-KYC sub-accounts.** The partner creates a sub-account per end user with `shareKyc: true`, and each sub-account carries the main account's verification. WhiteBIT verifies the partner during [Institutional Onboarding](/institutional/onboarding) (KYB); the partner verifies its own end users. Leave `email` out of the create request: a request with `email` starts the invitation flow even with `shareKyc: true`. No invitation, activation or KYC URL step applies: the sub-account is active at creation, and `spotEnabled` and `collateralEnabled` apply at once. Build with [Sub-Accounts](/products/sub-accounts/overview) and the [Embedded Trading integration guide](/guides/sub-account-integration), skipping its end-customer KYC steps.

## Payment and payout flows

Fund-movement mechanics, with parameters and code examples, are in the
[Sub-Accounts quickstart](/products/sub-accounts/quickstart) and the
[Payment Integration guide](/guides/payment-integration). Each diagram below covers one end user's sub-account and
names the key that signs each request: the main-account key or the sub-account's own key.

<Note>
  Fiat deposits and withdrawals operate on the **main account** (institutional fiat access), from and to
  the partner's own bank account only. End users' fiat stays in the partner's own system.
</Note>

<Warning>
**Compliance requirements that affect the requests:**
- EEA withdrawals require a `travelRule` object; in the sub-account models the partner submits it
  for each sub-account withdrawal it initiates. Inbound EEA/Turkey deposits are held until
  verification completes. See [Travel Rule](/concepts/travel-rule).
- For EEA users, use USDC or EURI, not USDT. See [Regulatory Compliance](/institutional/compliance).
</Warning>

### Wallet creation

Wallet creation runs once per end user: the sub-account, its `type: 2` API key with the deposit-address URL enabled, and a deposit address per ticker and
network. Managed sub-accounts add the activation and KYC URL steps from the
[customer onboarding flow](/guides/sub-account-integration#customer-onboarding-flow): the API key and deposit addresses
can be created once the end user activates the sub-account, and only transfers from the main account wait for the KYC
approval. Shared-KYC sub-accounts skip both steps.
WhiteBIT and the partner agree the KYC reliance setup during onboarding; see
[Build path per variant](#build-path-per-variant).

```mermaid
sequenceDiagram
    autonumber
    participant U as End user
    participant P as Partner backend
    participant W as WhiteBIT

    alt Managed sub-accounts
        P->>W: POST /api/v4/sub-account/create<br/>(main-account key, shared KYC off,<br/>end user's email, permission set)
        W-->>P: Sub-account id
        W->>U: Invitation email
        U->>W: Open the link<br/>and set a password
        loop Until the sub-account is activated
            P->>W: POST /api/v4/sub-account/list<br/>(main-account key)
            W-->>P: Sub-account activation state
        end
    else Shared-KYC sub-accounts
        P->>W: POST /api/v4/sub-account/create<br/>(main-account key, shared KYC on,<br/>no email, permission set)
        W-->>P: Sub-account id
    end
    P->>W: POST /api/v4/sub-account/api-key/create<br/>(main-account key, key name,<br/>deposit and withdrawal key)
    W-->>P: API key and secret<br/>(the secret is shown only at creation)
    opt Restrict the key to known IPs
        P->>W: POST<br/>/api/v4/sub-account/api-key/ip-address/create<br/>(main-account key, IP address for the key)
    end
    P->>W: POST /api/v4/sub-account/api-key/edit<br/>(main-account key, switch on<br/>/api/v4/main-account/address)
    W-->>P: Key updated
    P->>W: GET /api/v4/public/assets<br/>(public, no key)
    W-->>P: Deposit availability<br/>and networks per ticker
    loop Each depositable ticker and network to offer
        P->>W: POST /api/v4/main-account/address<br/>(sub-account key, currency and network)
        W-->>P: Deposit address, plus memo<br/>where the currency requires one
    end
    P->>P: Store end user, sub-account id,<br/>key, addresses and memos
    Note over P,W: Crypto deposits to sub-accounts work<br/>once the account manager enables<br/>sub-account deposits for the account
    opt Managed sub-accounts
        P->>W: POST /api/v4/sub-account/kyc-url<br/>(main-account key, sub-account id)
        W-->>P: Temporary KYC URL
        P->>U: Pass the KYC URL
        U->>W: Complete the WhiteBIT verification
        loop Until the verification is complete
            P->>W: POST /api/v4/sub-account/list<br/>(main-account key)
            W-->>P: Verification state
        end
        P->>W: POST /api/v4/sub-account/edit<br/>(main-account key, full permission set)
        Note over P,W: Transfers from the main account<br/>to the sub-account work only<br/>after the KYC is approved
    end
```

### Deposits

The diagram follows one deposit from the address shown to the end user to a final status.

```mermaid
sequenceDiagram
    autonumber
    participant U as End user
    participant P as Partner backend
    participant W as WhiteBIT
    participant B as Blockchain

    P->>U: Deposit address<br/>(+ memo)
    U->>B: Send funds on-chain
    B-->>W: Deposit
    opt Webhook set up on the sub-account
        W->>P: Deposit webhook<br/>(retried, no replay)
    end
    loop On a schedule, per sub-account
        P->>W: POST /api/v4/<br/>main-account/history<br/>(sub-account key)
        W-->>P: Deposit records,<br/>every status
        P->>P: Skip records whose<br/>status has not<br/>changed
        alt Successful (3, 7), final
            P->>P: Mark credited,<br/>stop tracking
        else Canceled (4), final
            P->>P: Offer the refund flow
        else Canceled (9), final
            P->>P: Mark canceled,<br/>stop tracking
        else Any other status
            P->>P: Act on the status,<br/>keep tracking
        end
    end
```

A sub-account counts as a separate account and can have its own webhook, created at whitebit.com only: the main account switches the session to the sub-account and creates the webhook there. The main account's webhook does not receive sub-account events, and payloads carry no sub-account identifier. Webhook delivery is retried but
has no replay, so poll the deposit history of each sub-account on a schedule as well, even when a webhook is configured.
Use `POST /api/v4/main-account/history` with `transactionMethod: 1`, signed with the sub-account's API key. Deduplicate by `uniqueId`. Act on each deposit status as the [Deposit status state machine](/guides/payment-integration#deposit-status-state-machine) describes. Not every deposit ends credited: some end canceled, and some stay in status 21 (on hold) or 22 (uncredited) before reaching a final status. See [Webhooks](/platform/webhook) for signatures and delivery semantics. API
[rate limits](/api-reference/rate-limits) apply per endpoint.

The `main` amount from `POST /api/v4/sub-account/balances` includes deposits credited before the network fully confirms
the deposits. The sub-account's key reads the part still held back as `pending_deposit_amount` from
`POST /api/v4/main-account/balance`, once `/api/v4/main-account/balance` is switched on for the key with
`POST /api/v4/sub-account/api-key/edit`. The held part cannot be withdrawn to a blockchain address or moved to the
Collateral balance until the network confirms the deposit.

### Crypto purchases with fiat

In a purchase, the partner debits the end user's fiat in the partner's own system and transfers the crypto from the
main account to the sub-account. For a managed sub-account, WhiteBIT refuses the transfer until the end user's KYC is
approved, and the refusal names the `to` field; offer purchases only after the approval.

<TransferNoIdempotency />

See [Retry strategy by error type](/api-reference/rate-limits#retry-strategy-by-error-type) for the retry rule of each
error type.

```mermaid
sequenceDiagram
    autonumber
    participant U as End user
    participant P as Partner backend
    participant F as Partner fiat system
    participant W as WhiteBIT

    U->>P: Buy crypto with fiat
    P->>W: POST /api/v4/main-account/balance<br/>(main-account key, currency)
    W-->>P: The main account's Main balance for the ticker
    Note over P,W: Transfers to a sub-account draw<br/>from the main account's Main balance<br/>and credit the sub-account's Main balance
    P->>F: Debit the end<br/>user's fiat
    P->>P: Record the transfer and<br/>the time before the call
    P->>W: POST /api/v4/sub-account/transfer<br/>(main-account key,<br/>main account to sub-account)
    alt 200, transfer accepted
        W-->>P: Transfer ID
        P->>P: Store the transfer ID with the purchase
    else Timeout or 5xx
        P->>W: POST /api/v4/sub-account/transfer/history<br/>(main-account key, sub-account ID,<br/>main account to sub-account)
        W-->>P: Transfers, newest first
        alt One clear match on direction, currency and amount, after the request
            P->>P: Store its transfer ID and do not resend
        else No match, or an ambiguous match
            P->>P: Manual check,<br/>no automatic resend
        end
    end
```

### Crypto sales for fiat

In a sale, the partner transfers the crypto from the sub-account's Main balance to the main account and credits the
end user's fiat once WhiteBIT accepts the transfer with a `200` response; the balances change a moment later. After a
timeout or a `5xx`, the partner checks the transfer history: one clear match counts as the transfer, and no match or an
ambiguous match is a manual check, not an automatic resend.

```mermaid
sequenceDiagram
    autonumber
    participant U as End user
    participant P as Partner backend
    participant F as Partner fiat system
    participant W as WhiteBIT

    U->>P: Sell crypto for fiat
    P->>W: POST /api/v4/sub-account/balances<br/>(main-account key, sub-account id, currency)
    W-->>P: main, spot and collateral amounts for the ticker
    P->>P: Check that the main amount covers the sale
    Note over P,W: A transfer to the main account draws<br/>from the sub-account's Main balance only
    P->>P: Record the transfer and<br/>the time before the call
    P->>W: POST /api/v4/sub-account/transfer<br/>(main-account key,<br/>sub-account to main account)
    alt 200, transfer accepted
        W-->>P: Transfer ID
        P->>F: Credit the end user's fiat
    else Timeout or 5xx
        P->>W: POST /api/v4/sub-account/transfer/history<br/>(main-account key, sub-account ID,<br/>sub-account to main account)
        W-->>P: Transfers, newest first
        alt One clear match on direction, currency and amount, after the request
            P->>F: Credit the end user's fiat
        else No match, or an ambiguous match
            P->>P: Manual check: no resend,<br/>no fiat credit until resolved
        end
    end
```

### Withdrawals

The sub-account's `type: 2` key creates each withdrawal, and the main-account key confirms it before processing
starts. The account manager enables the sub-account withdrawal endpoints.
[Sub-account withdrawal approval](/products/sub-accounts/quickstart#sub-account-withdrawal-approval) gives the request for each approval step.
A waiting withdrawal does not expire and sends no webhook: find it in the [unconfirmed-withdrawals list](/api-reference/sub-accounts/list-unconfirmed-sub-account-withdrawals) with the main-account key.

<SubAccountWithdrawal />

Act on each withdrawal status as the [Withdrawal status state machine](/guides/payment-integration#withdrawal-status-state-machine) describes.

### Conversion

Conversion on a sub-account uses the requests in [Convert balances](/platform/convert#balances) and
[Conversion in the withdrawal flow](/guides/payment-integration#conversion-in-the-withdrawal-flow), signed with the
sub-account's key, on the sub-account's Trade balance. The partner transfers the source currency from the Main balance to
the Trade balance and requests the estimate after the transferred amount shows on the Trade balance. Before a
withdrawal or a sale, the partner transfers the converted amount back to the Main balance, because the withdrawal endpoints
and a transfer to the main account both draw from the sub-account's Main balance only. The transfer to Trade needs the
sub-account's spot permission (`spotEnabled`). The main account's one-time acceptance of the Convert terms on whitebit.com
covers its sub-accounts; sub-accounts do not accept the terms separately.

Every URL group starts switched off on a new sub-account key, so before the first conversion the partner enables
`/api/v4/convert/estimate`, `/api/v4/convert/confirm`, and the balance transfer `/api/v4/main-account/transfer` on the
sub-account's key with [Edit Sub-Account API Key](/api-reference/sub-accounts/edit-sub-account-api-key), signed with the main-account key.

## API key lifecycle

The [14-day deactivation of unused keys](/best-practices/security#key-rotation) applies to sub-account keys too, and any
authenticated request, such as a deposit history poll, resets the timer.

<KeyCreateNoResponse />

```mermaid
flowchart TD
    Create["POST /api/v4/sub-account/api-key/create<br/>main-account key, deposit and withdrawal key, key name<br/>up to 50 keys per sub-account"]
    Create -->|"Response received"| Store["Store the API secret<br/>shown only at creation"]
    Create -->|"Timeout, no response"| Find["POST /api/v4/sub-account/api-key/list<br/>main-account key, newest key first"]
    Find --> Found{"Listed key with<br/>the requested name?"}
    Found -->|"Yes, the list never returns its secret"| Orphan["POST /api/v4/sub-account/api-key/delete<br/>main-account key, the orphan key"]
    Found -->|"No"| Create
    Orphan --> Create
    Store --> Urls["POST /api/v4/sub-account/api-key/edit<br/>main-account key, enable the URLs the key uses"]
    Urls --> Ip["POST /api/v4/sub-account/api-key/ip-address/create<br/>main-account key, optional IP whitelist"]
    Ip --> Use["Signed requests with the key,<br/>such as the deposit history polls,<br/>each reset the 14-day timer"]
    Use -->|"POST /api/v4/sub-account/api-key/list, main-account key"| Check{"Key enabled?"}
    Check -->|"Yes"| Use
    Check -->|"No"| Reset["POST /api/v4/sub-account/api-key/reset<br/>main-account key, same key and secret,<br/>URL access and IP whitelist kept"]
    Reset --> Use
```

## End-user offboarding

Offboarding empties the sub-account through a final withdrawal or a sale, then the main-account key blocks it. The
sub-account's key creates the final withdrawal and the main account confirms it, as in [Withdrawals](#withdrawals).
A sale follows [Crypto sales for fiat](#crypto-sales-for-fiat). The partner keeps the end user's mapping to the
sub-account and its addresses.

## Testing

WhiteBIT does not offer a public testnet or sandbox. Test on the live API with minimum amounts,
and check per-asset minimums via the [Asset Status](/api-reference/market-data/asset-status-list)
endpoint first. Where the response includes `limits`, a crypto deposit is checked against the network minimum (`limits.deposit.<network>.min`). A test deposit below the network
minimum is not credited at once: it waits in status 22, and unless the deposits to the same address add up to the minimum, it is canceled with status 9 after 7 days. The WhiteBIT Codes flow is a low-risk way to try a real signed call on a small
amount (see [Recipes](/guides/waas-recipes)).
