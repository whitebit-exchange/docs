Answers to common questions about WhiteBIT Crypto-as-a-Service (CaaS).

## Scope and model

### What CaaS includes

CaaS covers a deposit address per end user, crypto payouts, and conversion with Convert, run from the
partner's own WhiteBIT account and offered under the partner's own brand; fiat is added after fiat
onboarding. See the [CaaS overview](/guides/caas-overview).

### Account model

CaaS runs on the partner's own WhiteBIT account: the partner issues a deposit address per end user and
keeps an end-user ledger. See [Integration models](/concepts/integration-models) and
[Verification split](#verification-split).

### CaaS, sub-accounts, and Fast API Key

Sub-accounts and Fast API Key are separate from CaaS: a sub-account per end user under the partner's
account is Model A, used by [Wallet-as-a-Service](/guides/waas-overview) and Embedded Trading, and a
partner-scoped API key on an end user's own WhiteBIT account is
[Fast API Key via OAuth](/guides/fast-api-key-integration). See
[Integration models](/concepts/integration-models).

### End-customer capabilities

End customers can create crypto wallets, store crypto in institutional custody, buy and sell with fiat, and send and receive crypto. See [What end customers can do](/guides/caas-overview#what-end-customers-can-do).

## Deposit addresses

### Crypto deposit enablement

The partner's main account accepts crypto deposits after onboarding. Issuing a deposit address per end
user uses `create-new-address`, which the account manager enables on request. See the
[Integration guide](/guides/caas-integration#prerequisites).

### Address limits

Each `create-new-address` call creates a new address, with no limit on the number of addresses, so store every
address against its end user. See
[Address issuance and end-user mapping](/guides/caas-integration#address-issuance-and-end-user-mapping).

### Lost address responses

After a timeout or a `5xx` response from `create-new-address`, the address may already exist and still credit
deposits to the account, but no endpoint returns the address. Store each address before showing it, show no
address after a timeout, and request a new one. See
[Address issuance and end-user mapping](/guides/caas-integration#address-issuance-and-end-user-mapping).

### Memo networks

On memo networks, each `create-new-address` call returns the same address with a new memo, so the memo
identifies the end user. Store the memo together with the address, show both exactly as issued, and match each
deposit by address plus memo. A deposit with a wrong memo is credited to whichever account owns that memo; a
deposit without a memo, or with a memo no account owns, is not credited to any account and appears in no history. See the [Integration guide](/guides/caas-integration#address-issuance-and-end-user-mapping).

### End-user offboarding

When an end user leaves the service, allow a reasonable period to withdraw or convert the end user's crypto, then
convert what remains and credit the proceeds to the end user in the partner ledger. The API provides no way to
close or deactivate an issued deposit address, and the address keeps crediting deposits with no expiry, so keep
the address mapped to the end user. See
[End-user offboarding](/guides/caas-integration#end-user-offboarding).

## Deposits and reconciliation

### When to credit an end user

Credit an end user on the `deposit.processed` webhook, or a successful status in the history;
`deposit.accepted` and `deposit.updated` report progress only. Part of a new deposit can stay held until the
network fully confirms it — see [Held deposits](#held-deposits) and
[Deposits and crediting](/guides/caas-integration#deposits-and-crediting).

### Missed webhooks

Webhooks have no replay. Page the deposit and withdrawal history on a schedule and match the records
locally against the stored addresses. See
[Operating the integration](/guides/caas-integration#operating-the-integration).

### Held deposits

Part of a new deposit can stay held until the network fully confirms it. Withdrawals cannot draw on held
funds, and the withdrawable balance reports the hold for the whole account, not for each end user. See
[Deposits and crediting](/guides/caas-integration#deposits-and-crediting).

### Travel Rule holds

For EEA and Turkey accounts, inbound crypto deposits are held until Travel Rule verification completes,
and no webhook reports these status changes. See
[Travel Rule holds on deposits](/guides/caas-integration#travel-rule-holds-on-deposits).

## Payouts and fees

### Fee-inclusive and fee-on-top withdrawals

`/withdraw` deducts the fee from the amount, so the recipient receives the amount minus the fee;
`/withdraw-pay` sends the exact amount and charges the fee on top. See
[Payouts](/guides/caas-integration#payouts).

### Transfers between the partner's end users

Settle a transfer between two of the partner's end users in the partner ledger: the withdrawal endpoint
rejects a withdrawal to one of the account's own deposit addresses. See
[Payouts](/guides/caas-integration#payouts).

### Withdrawal IDs

Store each payout's withdrawal ID before sending the request, and never use one ID for two payouts. See
[Operating the integration](/guides/caas-integration#operating-the-integration).

## Onboarding and access

### Onboarding phases

Institutional onboarding has two phases: Phase 1 grants crypto operations access after KYC of the director or responsible person and KYB of the company; optional Phase 2 adds fiat access ([Fiat access via SEPA](#fiat-access-via-sepa)). See [Institutional Onboarding](/institutional/onboarding).

### Fiat access via SEPA

Fiat access is added in Phase 2 of institutional onboarding and runs through the partner's WhiteBIT account: SEPA withdrawals, and API-generated EUR deposit invoices once the account manager enables the invoice endpoint. See the [On/Off-Ramp guide](/guides/on-off-ramp-integration).

### Crypto Lending access

Fixed and Flex lending endpoints are restricted to B2B partners and return a permission error until access is granted. Request access through the account manager. See [Crypto Lending](/products/lending/overview).

### API base URL and regions

The global REST base URL is listed in the [Partner FAQ](/guides/partner-faq#api-base-url); the regional
environment is confirmed during onboarding.

### Test environment availability

WhiteBIT does not offer a public testnet or sandbox — see the
[Partner FAQ](/guides/partner-faq#sandbox-availability) and the
[Go-Live Checklist](/best-practices/go-live-checklist).

### Rate limits

Rate limits are set per scope and per endpoint rather than as a single global value. See the
[Partner FAQ](/guides/partner-faq#how-rate-limits-are-applied) and [Rate limits](/api-reference/rate-limits).

## Security and compliance

### Security certifications

WhiteBIT's security certifications are listed in [Regulatory Compliance](/institutional/compliance); custody is described under [Security and compliance](/guides/caas-overview#security-and-compliance).

### Verification split

The partner verifies its own end users; WhiteBIT verifies the partner during institutional onboarding
(KYB). See [Integration models](/concepts/integration-models#partners-own-account).

### MiCA and Travel Rule for EEA end users

For EEA users, MiCA restricts some stablecoin operations — USDT deposits, withdrawals, and WhiteBIT Codes are unavailable, and USDC and EURI are the documented alternatives. The Travel Rule governs crypto transfers for EEA and Turkey accounts. See [Regulatory Compliance](/institutional/compliance) and [Travel Rule](/concepts/travel-rule).

### Restricted jurisdictions

Which jurisdictions are restricted or prohibited for the partner and its end customers is confirmed case by case with `compliance@whitebit.com`; bring the target regions to the first onboarding conversation so the applicable regime (including MiCA and Travel Rule scope) can be assessed. See [Restricted jurisdictions](/institutional/compliance#restricted-jurisdictions).

### Data Processing Agreement

A Data Processing Agreement (DPA) is available on request; WhiteBIT processes data in the European Union. Request it via `compliance@whitebit.com`. See [Regulatory Compliance](/institutional/compliance).

## Support

### Support contacts

The assigned account manager is the primary contact. Programs and onboarding go to `institutional@whitebit.com`; compliance, VASP, and DPA matters go to `compliance@whitebit.com`. Platform questions are answered at [help.whitebit.com](https://help.whitebit.com), and API documentation is on docs.whitebit.com.
